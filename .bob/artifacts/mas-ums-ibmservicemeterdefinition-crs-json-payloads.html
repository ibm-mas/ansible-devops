MAS → UMS: IBMServiceMeterDefinition CRs & JSON Payloads

Derived from existing MAS Segment/BAS payloads. The unit field in MAS payloads maps to metricName in UMS.

Field Mapping: MAS payload → UMS IBMServiceMeterDefinition

Every MAS event has a unit property that becomes the UMS metricName. Other fields map as follows:

MAS payload fieldUMS CR fieldUMS JSON payload fieldNotes
unitspec.data.metricName—Core mapping. e.g. AppPoints, Licenses, Users, Capability Values
unitDescriptionspec.data.metricDescription—Human-readable description from MAS
productIdspec.data.productId—e.g. 5737-M66 or 5900-AMG
productTitlespec.data.productName—e.g. Maximo Application Suite
instanceIdspec.data.instanceId—Unique MAS instance identifier
quantity—metricQuantityActual measured value, sent hourly
unitMetadata.data.*spec.breakdownDefsbreakdowns or extra fieldsSub-metric breakdown data (user types, capability sub-metrics)
frequency: Hourlyprocessing: MAX or ADD—Determines daily aggregation strategy

1. Contractual Metrics

Reported as Account Contractual Usage events. These appear in compliance/audit snapshots. MAS reports AppPoints as the contractual unit.

AppPoints — Account Level
CONTRACTUAL
IBMServiceMeterDefinition CR
apiVersion: operator.ibm.com/v1
kind: IBMServiceMeterDefinition
metadata:
  name: mas-apppoints-metering-definition
  namespace: mas-inst1-core   # product namespace
spec:
  mappingId: mas-apppoints-5737m66-inst1
  processing: MAX             # high-water mark per hour
  data:
    instanceId: "<source>-<instanceName>"  # e.g. a2d89e0861e6-a311671
    productId: 5737-M66
    productName: Maximo Application Suite
    metricName: AppPoints
    metricDescription: Account level AppPoint usage
    metricType: CONTRACTUAL
JSON Payload (POST /api/v1/event)
[
  {
    "mappingId": "mas-apppoints-5737m66-inst1",
    "instances": [
      {
        "metrics": [
          {
            "measurementTimestamp": "2025-12-12T21:00:20Z",
            "metricQuantity": 10,
            "quantityEntitled": 68
          }
        ]
      }
    ]
  }
]
Note: quantity from MAS = active AppPoints used. quantityEntitled is included for context. Processing MAX takes the peak hourly value as the daily metric.

2. Adoption Metrics

Reported as Account Adoption Usage events. Not in compliance snapshots — used for product telemetry, usage tracking, and dashboards. Three metric units: Licenses, Users, and Capability Values.

Licenses — Account Level License Usage
ADOPTION

apiVersion: operator.ibm.com/v1
kind: IBMServiceMeterDefinition
metadata:
  name: mas-licenses-metering-definition
  namespace: mas-inst1-core
spec:
  mappingId: mas-licenses-5737m66-inst1
  processing: MAX
  breakdownDefs:
    - breakdownBy:
        name: licenseTypeBreakdown
      groupBy:
        - licenseType
      source: licenseCount
      processing: MAX
  data:
    instanceId: "<source>-<instanceName>"
    productId: 5737-M66

3. Low-Level Adoption Events (Object-Level)

Fired on user actions — object creates/updates in Manage. These have no unit or quantity field — they are count-based events. The objectType becomes the metric name.

Object Events — Work Order / Material Receipt / Purchase Order / Inspection / etc.
LOW-LEVEL ADOPTION
IBMServiceMeterDefinition CR (Work Order example)
apiVersion: operator.ibm.com/v1
kind: IBMServiceMeterDefinition
metadata:
  name: mas-workorder-events-definition
  namespace: mas-inst1-core
spec:
  mappingId: mas-workorder-5900amg-inst1
  processing: ADD             # count is cumulative per day
  data:
    instanceId: "<source>-<instanceName>"
    productId: 5900-AMG
    productName: Maximo Application Suite SaaS
    metricName: Work Order    # objectType from MAS payload
    metricDescription: Work Orders created or updated in Manage
    metricType: ADOPTION
Create one CR per objectType: Work Order, Material Receipt, Purchase Order, Inspection, Issues and Transfers, Workflow. Use ADD since each event = +1 occurrence.
JSON Payload (one event = quantity 1)
[
  {
    "mappingId": "mas-workorder-5900amg-inst1",
    "instances": [
      {
        "metrics": [
          {
            "measurementTimestamp": "2025-12-12T20:24:49Z",
            "metricQuantity": 1,
            "processType": "mobile"
          }
        ]
      }
    ]
  }
]
Batching: Accumulate events over the reporting interval and send metricQuantity: N (count) per batch, rather than one call per event. Include processType only when present (e.g. "mobile" for mobile work orders/inspections).

Key design decisions:
• unit → metricName: The MAS unit field (AppPoints, Licenses, Users, Capability Values) maps directly to spec.data.metricName in the CR.
• Contractual vs Adoption: Only AppPoints events (Account Contractual Usage) use metricType: CONTRACTUAL — everything else is ADOPTION.
• Low-level events have no unit: Use objectType as metricName with processing: ADD and batch-count per interval.
• One CR per distinct metric+capability combination: Capability Values for Manage and Monitor have different unitMetadata.data keys, so they need separate CRs/mappingIds.
• instanceId: Set to the MAS payload's instanceId field (<source>-<instanceName>).
